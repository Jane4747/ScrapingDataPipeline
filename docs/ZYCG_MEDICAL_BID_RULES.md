# 央采医卫数字化中标：采集设计与口径

本轮目标：拿到 2026 年以来中央国家机关政府采购中心（下称“央采中心”）组织的医卫数字化项目中标结果，
落成一张八列表：项目名称、产品、招标单位、客户标签、中标单位、运营商类型、中标金额（万元）、场景。

代码：`pipeline/research/zycg.py`；共用口径：`pipeline/research/bid_common.py`；
测试：`tests/test_zycg_medical_bid.py`；
想法树：`idea-trees/20261027-230958/`（由 `scripts/write_zycg_tree.py` 生成，含入口勘察、链路、分窗、口径、执行与缺口）。

> 同口径的后续采集：北京、雄安两地见 `docs/BJXA_MEDICAL_BID_RULES.md` 与想法树 `idea-trees/20261027-bjxa-medical/`。
> 八列口径已抽到 `bid_common`，两地与央采共用；该轮发现「设备维保／医用设备购置」等会被 `DIGITAL` 放行，
> 已单列复核清单但**未改**共享口径，改动会同时影响本表这 109 条的统计。

## 一、入口勘察结论（先证明能不能采，再谈怎么采）

| 入口 | 实测 | 结论 |
|---|---|---|
| `www.zycg.gov.cn` 首页 | 200，约 173KB 静态页 | 可达，但采购公告列表不在静态 HTML 里 |
| `www.zycg.gov.cn/freecms/rest/v1/notice/selectInfoMore.do`（列表 JSON） | 任何参数组合都返回 `{"code":"-1","msg":"公告列表查询失败"}`，空 `noticeType` 同样报错；POST 返回 405 | **服务端拒绝，不可用**。参数取自页面内联脚本（siteId `6f5243ee-…`、channel `d0e7c5f4-…`、`noticeType=2` 即中标成交公告），不是我们拼错 |
| `www.zycg.gov.cn` robots.txt | 404（无规则即未禁止） | 无 extra 约束 |
| `ggzy.zycg.gov.cn/fe_zccz/notice_matter` | 200 但是“国有资产处置信息公开系统”的 SPA 壳 | 与采购公告无关 |
| `oldpt.zycg.gov.cn` | 302 自跳自身 | 旧平台不可用 |
| **`search.ccgp.gov.cn/bxsearch`** | 200，可按 `agentName=中央国家机关政府采购中心` 精确过滤，带发布时间/采购人/代理机构/地区/公告类型 | **采用**。与央采本站同源：正文末尾即“中央国家机关政府采购中心”署名 |
| `www.ccgp.gov.cn/cggg/zygg/zbgg/`（中央公告列表） | 只保留最近 5 天（25 页 × 20 条）滚动窗口，更早无月度入口（目录 403） | 不可回溯 2026 全年，只能做近端校验 |

## 二、采集链路

```
search.ccgp.gov.cn/bxsearch?agentName=中央国家机关政府采购中心
        &timeType=6&start_time=2026:01:01&end_time=今天&page_index=N
        ↓ 每页 20 条，共 4524 条（2026-01-01~2026-10-27）≈ 227 页
列表行自带：标题 / 发布时间 / 采购人 / 代理机构 / 公告类型 / 地域
        ↓ 只保留 /zbgg/（中标公告）与 /cjgg/（成交公告）
标题级过滤：医卫主体 ∩ 数字化标的，剔除后勤/纯设备/工程
        ↓ 候选逐条取详情 www.ccgp.gov.cn/cggg/zygg/{zbgg|cjgg}/YYYYMM/tYYYYMMDD_xxxx.htm
正文抽取：项目编号 / 项目名称 / 采购方式 / 预算金额 / 供应商 / 中标金额 /
          主要标的（名称·品牌·型号）/ 采购人信息 / 采购执行机构
        ↓
打标：客户标签、运营商类型、场景 → 八列表 + 明细页
```

- **央采判定不靠猜**：检索参数就是代理机构字段，命中即央采中心组织；详情页再用“采购执行机构信息”二次确认。
- **只取结果公告**：招标公告、更正公告、终止公告不进表（更正可能改金额，属已知边界）。
- **节流与合规**：复用 `pipeline/research/fetch.py` 的 `Fetcher`（robots 检查、单站点最小间隔、遇到 401/403/429 直接判 `blocked` 不重试不绕过、UA 自报 `CAICTMedicalResearchBot`）。
- **遇到挑战就停并续采**：检索站在高频请求下会返回访问挑战页。实测 1.1s 间隔在第 31 页被拦；改为 3.0s + 随机抖动后继续跑。已取页面落盘 `cache/page-NNNN.html`，重跑直接命中缓存，不重复请求；`blocked_at_page` 写入结果 JSON，便于判断“是不是全量”。
- **失败留痕**：发现阶段与详情阶段的失败逐条写入 `zycg_medical_bid.json` 的 `failures`，含阶段、状态码、URL、原因。

## 三、八列表的字段口径

| 列 | 取值 | 说明 |
|---|---|---|
| 项目名称 | 正文“项目名称”，去掉尾部“中标公告/成交公告” | 不用列表标题，避免带“（第二次）”之类后缀噪声 |
| 产品 | 主要标的表“主要投标标的名称”去重取前 4 项 | 取不到标的表时退化为场景词；不臆造品牌型号 |
| 招标单位 | 正文“采购人信息—名称” | 取不到时用列表行的采购人字段，两者都留 |
| 客户标签 | 按采购人名称规则分类 | 国家级医学科研/医疗机构、高校附属医院、中医/专科/综合医疗机构、妇幼保健、疾控、卫生行政/监管、医保、公共卫生（血液/急救）、军队、基层、其他 |
| 中标单位 | 正文“供应商名称”，多包用“；”连接 | 主金额只取首个金额，多包分项金额在明细页保留原文 |
| 运营商类型 | 中标单位名称含 中国移动/中移、中国电信、中国联通、中国广电 → 对应运营商；否则“非运营商” | 按工商名称判定，不做股权穿透 |
| 中标金额（万元） | “中标（成交）金额”折算万元 | 亿元×10000、元÷10000；保留原文列便于复核 |
| 场景 | 标题+标的文本按优先级命中 | 云与算力、数据中心与机房、网络与链路、信息安全、存储与备份、影像与检验、电子病历与HIS、互联网医院与远程医疗、人工智能、应用系统与平台、运维与技术服务、终端与办公设备 |

**归类只做一层**：场景取首个命中类别，不做多标签打分；客户标签取名称中最具体的一类（专科优先于综合）。

## 四、明确不覆盖的范围

1. 央采**电子卖场/批量集采/电子询价**的成交数据（走 zycg 商城与另一个系统，代理机构字段不指向央采中心，本链路抓不到）。
2. 中央单位**委托社会代理机构**的项目（代理机构不是央采中心，如中招国际、国信招标），不属“央采”口径。
3. 地方政采、军队采购、药械集采：另有来源，不在本轮。
4. 金额只看公告口径；合同变更、追加、结算金额未纳入。
5. 项目“是否真正落地/验收”不做推断，公告只是中标事实。

## 五、复现

```bash
# 列表发现 + 过滤 + 详情 + 出表（按月切窗，约 8-12 分钟）
python -m pipeline.research.zycg --start 2026-01-01 --end 2026-10-27 \
    --output outputs/zycg-2026-medical/run-YYYYMMDD --delay 2.5

# 只验证发现与过滤，不取详情
python -m pipeline.research.zycg --dry-run --max-pages 5

# 限流期间：离线合并已落盘的列表页缓存，不再请求检索站
python -m pipeline.research.zycg --from-cache outputs/zycg-2026-medical/run-A,outputs/zycg-2026-medical/run-B \
    --output outputs/zycg-2026-medical/final
```

输出：`央采医卫数字化中标_2026.xlsx`（两张表：主表八列、明细页含编号/预算/地域/链接）、
同名 `.csv`（UTF-8 BOM，直接进 Excel）、`zycg_medical_bid.json`（逐条记录、排除项及原因、失败台账、运行日志）。

## 六、限流实测与分窗策略

| 尝试 | 参数 | 结果 |
|---|---|---|
| 单窗口全量 | 2026-01-01~2026-10-27，delay 1.1s | 第 31 页被访问挑战打断 |
| 同窗口重试 | delay 3.0s | 跑到第 100 页被打断（覆盖到 8-13） |
| 冷却 7 分钟后 | 直接请求第 100/101/150 页 | 仍返回挑战页；同时间**窄日期窗第 1 页正常** |
| **按月切窗** | 每月一窗（每窗约 20-25 页） | 1-6 月全部跑通，7 月起端点再次限流 |
| 单补两个月 | 2026-07-01~2026-08-12，delay 5s | 两窗跑通，无挑战 |
| 缓存合并 | 三批缓存离线合并 | 4193 条公告，无新增请求 |

结论：检索站按请求总量限流，且对同一查询的深页（page_index ≥ 100）直接返回挑战页；
按月切窗后每窗 20-25 页，既能绕开深度上限，也把单次突发压低。被挑战时不绕过、不换 UA、
不加代理，靠 `cache/page-*.html` 已取页续采。
