# SearchingAgent 三平台采集与 Dagu 本次代码总结

本轮把央采、全国公共资源交易平台和北京公共资源交易平台接入同一套可恢复的采集与交付流程。新增7个文件、修改3个既有模块；Codex承接任务，Dagu显示三个来源进程的执行、日志和失败状态，最终统一输出22个字段。这里的并行能力来自独立采集进程；RSI自动改码评估和多模型自主协作仍是后续架构工作。

归档日期：2026-10-30（北京时间）。本次采集请求固定为 **2024-01-01至2026-10-29，按公告发布日期筛选医疗数字化采购信息**，没有因归档日期变化扩大采集范围。最新保存的资料为 **1,082条公告，整体partial**，不等于1,082个独立项目或全量覆盖。

## 关键问题与修复

- **北京历史数据入口**：常规列表只能覆盖近期页面；改用官网公开的`/elasticsearch/search`，采用实际`scope=title`参数与完整医卫词，按月分页并验证返回日期。系统TLS保留证书校验。
- **全国历史接口与超时**：历史数据走`/his/information/pubTradingInfo/getTradList`，较新数据走当前接口，跨边界月份无缝拆分；仅对多日窗口的瞬时超时继续细分，单日失败保留为缺口。
- **央采末页与访问挑战**：按页面Pager总页数停止，避免多抓一页后误报重复；遇到访问挑战停止该源并保存断点。
- **Windows Dagu运行目录**：显式设置`DAGU_HOME`，让服务、队列和执行子进程读取同一目录；默认弹出`http://127.0.0.1:8098/`。
- **恢复和审计**：原始请求保持不变，兼容修复记入`code-revisions`；每次来源执行记录加载的代码版本，来源锁阻止重复写入。本次核对当前revision 5的8个受控文件哈希及原请求哈希全部一致。
- **表格数据一致性**：各来源计数按本次被接受的记录重算，防止并行写入进度导致总表与来源计数不一致。日期、金额为原生类型，未知值留空。

当前预算实现存在来源差异：全国和北京的API预算按本次执行限制，央采接入页数预算，尚未接入统一API与详情预算。扩展来源前应统一累计预算语义，不能把当前配置解释为三源统一累计请求上限。

## 输出字段与证据规则

时间、项目名称、产品、招标单位、客户标签、中标单位、运营商类型、中标金额（万元）、场景、评审专家、网址、公告类型、省份、项目编号、中标金额原文、信息缺口、标签依据、响应人资格要求（对供应商基本要求）、资格预审资质要求、来源平台、资格要求出处、原文文件。

其中前19项为用户要求，后3项为追溯字段。专家和资格按正文具体章节提取，证据记录网址、行号及文本哈希；项目编号与采购人均一致、资格内容版本唯一且来源公告不晚于目标公告时，才允许跨公告补充资格。冲突保留，不自动选定。采购预算不当作中标金额，非最终结果公告不填确定的中标事实，客户与场景标签仍是规则判断。
